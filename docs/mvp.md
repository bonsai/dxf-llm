# mvp.md — Minimum Viable Product 計画

## 目的

**実案件 1 棟が、実務でそのまま回ること。**
PoC が「技術的にできる」の証明なら、MVP は「仕事で使える」の証明。
期間: **2〜3 か月**。

---

## MVP の定義（これができたら MVP）

> **設計事務所/ゼネコンの担当者が、JWW/DXF を投げると
> ①数量表（Excel/CSV）と ②IFC（3D）が出て、
> ③「この壁は？」に自然言語で答えられる。
> しかも、手作業より速い。**

---

## 対象ユーザーとユースケース

| ユーザー | ユースケース | 提供物 |
|---|---|---|
| 設計事務所（木造） | 平面図 → 壁量・開口数量 | `Quantity Cloud` 相当 |
| ゼネコン積算 | 施工図 → 数量拾い（壁/床/開口） | CSV/Excel 出力 |
| 構造設計 | 建築図 → 構造モデル下地 | 節点・部材データ |
| 発注者説明 | 図面 → 3D プレビュー | IFC / glTF |

初期スコープは **「木造平面図 → 壁数量 + IFC」** に絞る。

---

## PoC との差分（MVP で足すもの）

| 項目 | PoC | MVP |
|---|---|---|
| 対象 | サンプル 1 枚 | 実案件 1 棟（複数階） |
| 分類 | ルールのみ | ルール + 軽量 ML |
| 出力 | 壁長のみ | 壁/床/開口/仕上 + Excel |
| 品質 | 動けば OK | テスト + 検証 + ログ |
| 運用 | 手元実行 | CLI + Docker + 設定 |
| LLM | 単発質問 | 会話 + 根拠提示（JSON） |
| 権限 | なし | プロジェクト単位の分離 |

## 機能要件

### 必須（Must）
- [ ] JWW/DXF 一括取り込み（フォルダ単位）
- [ ] 壁/柱/窓/ドアの自動分類（精度 85% 以上）
- [ ] 数量拾い: 壁長・壁面積・開口数・床面積
- [ ] Excel / CSV 出力（テンプレート準拠）
- [ ] IFC4 出力（BlenderBIM/IfcOpenShell で検証）
- [ ] LLM 質問応答（根拠 JSON 付き）
- [ ] YAML ワークフロー + CLI
- [ ] Docker イメージ（オフライン動作）

### 推奨（Should）
- [ ] レイヤ規約のユーザー設定（YAML）
- [ ] エラー時の修復ステップ（トポロジ修復）
- [ ] ログ・レポート（どの図元をどう解釈したか）
- [ ] 最小 Web UI（ドラッグ&ドロップ）

### 除外（Won't / 今回はやらない）
- [ ] 構造計算そのもの
- [ ] DWG 双方向編集
- [ ] 大規模 CDE 連携（API 接続は次段階）

---

## 非機能要件

| 項目 | 目標 |
|---|---|
| 処理速度 | 1 棟（10〜20 枚）を数分以内 |
| 精度 | 壁分類 85%+、数量誤差 5% 以内 |
| 移植性 | Windows/Linux、Python 3.10+、オフライン可 |
| 保守性 | テストカバレッジ 70%+、型ヒント必須 |
| セキュリティ | データ外部送信なし（ローカル LLM 可） |

## アーキテクチャ（MVP）

```
              ┌─────────────────────────────┐
   JWW/DXF ──►│  Workflow (DAG)              │
              │  parse → enrich → quantity   │
              │         → export_ifc/quantity │
              └───────────────┬─────────────┘
                              │
      ┌───────────────────────┼───────────────────────┐
      ▼                       ▼                       ▼
  Quantity(Excel)         IFC(3D)              LLM Query(API)
      │                       │                       │
      └───────────────────────┴───────────────────────┘
                      PluginRegistry + Hooks
```

- **Plugin**: `dxf_parser`, `semantic_enricher`, `quantity_takeoff`, `ifc_exporter`, `report_exporter`
- **Workflow**: YAML 定義、並列実行、リトライ
- **API**: FastAPI（`/analyze`, `/search`, `/convert`）

| 分類精度 | 85% 以上 |

---

## リスクと対処

| リスク | 対処 |
|---|---|
| レイヤ規約のばらつき | 案件ごとの設定 YAML + プリセット |
| 分類精度が伸びない | ルール優先 → 誤りだけ ML 補正 |
| IFC の主観（重さ/座標系） | 受け手（構造/積算）と仕様合意 |
| 現場の運用に乗らない | 既存フロー（Excel/PDF）に寄せる |
