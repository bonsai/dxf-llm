# aim.md — dxf-llm の目的と到達点

## 一行で

> **日本の建築 CAD 資産（JWW/DXF）を、Python + LLM で「読める・繋がる・自動化できる」構造化データに変える。**

---

## なぜやるか（Why）

| 現状の痛み | dxf-llm が目指す状態 |
|---|---|
| JWW/DXF は開く・編集する・繋げるが手作業 | パイプライン化してワンコマンドで処理 |
| 図面が AI に読めない（ベクタ・レイヤ規約が閉じている） | LLM が図面を検索・集計・生成できる |
| 数量拾い・法チェックが属人化 | ルール + LLM で再現可能な自動処理 |
| 2D 紙でしか説明できない | 3D / IFC / Web / ゲームへ一気通貫 |

---

## 最終的に目指すもの（North Star）

```
JWW/DXF ──► 構造化 JSON ──► LLM エージェント ──► 数量 / IFC / 3D / ゲーム
   ①            ②                ③                      ④
```

1. **解析** — JWW/DXF を CP932・レイヤ・色・線種まで保持して構造化
2. **意味付け** — 「線」を「壁・柱・窓・梁」へ自動分類（ルール + ML）
3. **エージェント化** — 自然言語で検索・集計・図形生成・修正
4. **多出力** — IFC / glTF / Three.js / Roblox / CSV / JSON を単一ソースから

---

## 非目標（やらないこと）

- AutoCAD/Revit の完全クローンを作る → **しない**（繋ぐ側に徹する）
- DWG の完全双方向編集 → **ODA / LibreDWG に委譲**
- 大規模 CDE / BIM 360 の置換 → **IFC と API で接続**
- 構造計算そのものの実装 → **SS3/SNAP 等へデータを渡す**

---

## 成功の定義（3 段階）

| 段階 | 到達点 | 判断材料 |
|---|---|---|
| **PoC** | 1 枚の JWW が 3D/IFC になり、LLM が質問に答える | デモが動く・再現手順がある |
| **MVP** | 実案件 1 棟が実務で回る | 手作業比の工数削減を数値で示せる |
| **事業** | 複数社が継続利用・課金 | 有償化率・ARR |

詳細は `poc.md` / `mvp.md` を参照。

---

## 技術スタック（aim）

- **解析**: `ezdxf`, `JWW2DXFConv`, `shapely`, `pyclipper`
- **幾何**: `build123d` / `CadQuery`, `OCC`
- **BIM**: `IfcOpenShell`, FreeCAD `Arch`, BlenderBIM
- **LLM**: `LangChain` / `LangGraph`, Qdrant, VLM (Qwen2-VL / GPT-4o)
- **可視化/出力**: `pyvista`, `trimesh`, `pygltflib`
- **基盤**: Python 3.10+, FastAPI, Docker（オフライン動作可）

---

## 原則（Principles）

1. **ローカルファースト** — 官公庁・大手ゼネコン社内でも動く
2. **オープン** — コアは OSS(MIT)。拡張・プラグインで差別化
3. **単一ソース** — 一つの構造化モデルから全出力を生成
4. **再現可能** — すべて YAML ワークフロー + テストで固定
5. **段階的** — PoC → MVP → 事業を飛ばさない
